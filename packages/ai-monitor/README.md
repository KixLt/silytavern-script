# TT | AI 请求监控（酒馆助手脚本）

监控 TauriTavern 每次访问 AI 的实际情况：**是否成功**、**发送了多少 token**、**接收了多少 token**、**缓存命中率**，以及耗时、首字延迟、token/s。

## 文件

| 路径 | 用途 |
| --- | --- |
| `src/tt-ai-monitor.js` | 面板源码（唯一需要手改的文件） |
| `scripts/build.mjs` | 打包脚本：源码 → 酒馆助手脚本 JSON |
| `dist/ai-monitor/TT-AI-Monitor.json` | 构建产物，离线导入用 |
| `dist/ai-monitor/tt-ai-monitor.js` | 构建产物，供 jsDelivr 当加载器脚本读取 |

## 安装

**推荐：加载器脚本**（自动跟随仓库更新）

1. 酒馆助手 ‣ 脚本 ‣ 新建脚本。
2. 内容只写一行:

   ```js
   import 'https://cdn.jsdelivr.net/gh/KixLt/silytavern-script@master/dist/ai-monitor/tt-ai-monitor.js'
   ```

3. 保存并启用。

**离线：导入 JSON**

1. 打开酒馆助手的「脚本库」面板。
2. 点导入（工具栏的文件图标），选择 `dist/ai-monitor/TT-AI-Monitor.json`。
3. 导入后脚本默认是**关闭**状态，手动打开开关。

两种方式装好后，顶部会出现「TT | AI 请求监控」，或点脚本按钮「显示/隐藏面板」随时开合。

脚本按钮：

- **显示/隐藏面板**
- **清空统计**

## 面板说明

面板分两个 Tab：

**实时** — 当前 / 最近一次请求的完整指标

```
● AI 监控                     5 条  –  ×
────────── 实时 ──────────┬────────── 历史 5 ──────────
┌──────────────────────────────────────────────────────┐
│ 成功  gemini-4-carbon · 7.1s · 247.9 tok/s · 首字 0.7s │
└──────────────────────────────────────────────────────┘
[发送(输入) 155.2k] [接收(输出) 1,760] [缓存命中 93.4%]
███████████████████████████████████████░
5 次 · ✓4 ✗1 · ↑597.5k ↓9,310 · 缓存 92.8% · 均耗 14s
```

- 两个 Tab 各占面板宽度的一半，Tab 栏固定在滚动区外，不随内容滚动。
- 状态文字（`成功/失败/请求中` + 模型·耗时·速度）包在与「发送」同款的全宽卡片里，占满一整行。
- 面板停靠在输入框上方与「楼层可见性」共用的那一行，高度由内容决定；内容区上限 `min(46vh, 340px)`，超出时只有中间滚动，标题栏与 Tab 栏固定。

**历史** — 最近 35 条请求，只显示成功/失败；点任意一条在页内展开详情

```
────────── 实时 ──────────┬────────── 历史 5 ──────────
✓  11:17:42                                   详情 ›
✓  11:17:42                                   详情 ›
✗  11:17:42                                   详情 ›
```

点开后与实时页同一套指标卡片，另附时间、模型、来源、耗时、首字延迟、token、缓存、日志 ID、错误原因，左上角「← 列表」返回。

- 顶部圆点：绿=成功，红=失败，黄=请求中；`×` 关闭面板（用脚本按钮「显示/隐藏面板」重新打开），`–` 折叠。
- 点标题栏（或 `–`）折叠，只剩标题行；与「楼层可见性」并排时本面板占剩下的宽度（左边那张窄条固定 300px），隐藏本面板后那一行只剩楼层可见性。
- **拖动标题栏**可以把面板从状态栏里拖出来，变成可以摆在任意位置的浮窗（位置和宽度记在 localStorage，下次打开还在原地）；**双击标题栏**回到输入框上方那一行。
- **发送 (输入)**：本次请求实际送入模型的 prompt token 数（提供方上报）。
- **接收 (输出)**：本次回复生成的 token 数；优先用楼层记录的 `extra.token_count`，缺失时用本地分词器计数。
- **缓存命中**：`cached_tokens / input_tokens`，即本次 prompt 有多少比例直接命中提示词缓存。
- 累计行：请求次数、成功/失败、累计输入/输出、按 token 加权的平均缓存命中率、平均耗时。
- 历史最多保留 35 条，超出后最旧的自动淘汰。
- 统计按聊天分开保存（localStorage），切换聊天自动切换数据；当前 Tab、折叠/隐藏状态全局记忆。

## 数据来源

1. **成败 / 耗时 / 模型**：TauriTavern 主进程的 LLM API 日志流
   `window.__TAURITAVERN__.api.dev.llmApiLogs.subscribeIndex()`。
   这就是「设置 → 开发者工具 → LLM API 日志」里能看到的那份记录，每次真实 HTTP 请求完成（或失败）都会推送一条。
   失败时还会用 `getPreview(id)` 取回错误原因。
2. **token 与缓存**：楼层消息的 `extra`
   - `extra.prompt_cache = { input_tokens, cached_tokens }`（由主进程从提供方的 usage 归一化而来，支持 OpenAI/Claude/Gemini/Responses 等）
   - `extra.token_count`（回复的 token 数）
   - `extra.time_to_first_token`（首字延迟，毫秒）

## 已知限制

- 提供方**不上报 usage** 时，发送 token 会用提示词管理器里本次组装的 token 数估算，并在数值后标注「估」。
- **缓存命中率**必须有 `cached_tokens` 才有意义；提供方不返回就直接显示 `—`，不会猜。
- 只写日志、不产生楼层的请求（如标题生成、部分静默生成）仍会统计成败与耗时，但没有 token 数据。
- 非 TauriTavern 环境（普通 SillyTavern）没有日志流，会自动退化为「事件模式」：只能统计成功请求，失败靠 `toastr` 错误提示推断。

## 二次开发

改 `src/tt-ai-monitor.js`，然后在本仓库根目录重新打包：

```bash
pnpm --filter @silytavern/ai-monitor build   # 只打这一个包
pnpm build                                   # 或所有包一起打
```

产物写到仓库根 `dist/ai-monitor/`。构建不会写入随机脚本 id，因此同一份源码永远产出同一份 JSON，CI 可以靠 `git diff` 判断是否需要回写产物。
